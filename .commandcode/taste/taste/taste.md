# Taste
- Never claim work is "complete" without executed evidence: do not say complete if the database was not actually tested, migrations not actually applied, APIs not exercised, build/tests not actually run, or browser flows not verified. Confidence: 0.95
- Distinguish explicitly between IMPLEMENTED, VERIFIED, and BLOCKED in status reports; a BLOCKED gate must never be reported as PASS. Confidence: 0.95
- Never fabricate test results, row counts, or acceptance evidence — report actual command output, real HTTP status codes, and real observed behavior only. Confidence: 0.95
- End substantial work with a concise, evidence-based completion report (status, what was verified, what is blocked/limited), and for every limitation distinguish genuine defect vs environment limitation vs tooling limitation vs intentionally unsupported. Confidence: 0.85
- Do not hide defects to make the build look green; a feature is not complete merely because the UI renders. Confidence: 0.9
- Never print, log, commit, or put real credentials/secrets into source, docs, screenshots, reports, or git; use environment variables and placeholders only. Confidence: 0.9
- Do not ask the user to paste a database password into chat; use an already-authorized local credential mechanism (e.g. a gitignored `.env`). Confidence: 0.85
- Do not weaken or bypass platform security (auth, pg_hba, permissions) to work around a blocker. Confidence: 0.85
- Frontend hiding is not security: every sensitive operation must be enforced server-side, and authorization must be tested directly (RBAC, IDOR, record-level access scope) rather than assumed. Confidence: 0.85
- Do not interrupt for confirmation on routine implementation steps; continue autonomously through all independent work, isolating genuine external blockers and proceeding with everything else. Confidence: 0.9
- Inspect the existing implementation thoroughly before writing new code, build a map of what exists/is incomplete/duplicated, and preserve correct existing work rather than rebuilding it. Confidence: 0.85
- Treat referenced/sibling projects as read-only; never modify them, and verify their integrity before declaring work complete. Confidence: 0.85
- Fix defects at the root cause: reproduce, diagnose, fix, add a regression test, re-run the affected tests and dependent workflows. Confidence: 0.85
- Prefer fixing an authoring-time defect in place (edit the source migration) over adding a permanent corrective forward migration when the chain has never been applied anywhere. Confidence: 0.7
- When building a new product in this product family, mirror the architecture and conventions of the existing fully-built sibling product closest to the domain. Confidence: 0.75
- No fabricated or placeholder product data: no mock/hardcoded business metrics, no fake API responses, no dead buttons, no invented map coordinates. Confidence: 0.85
- For database-backed apps: the migration tool (Flyway) is the schema authority; use Hibernate `ddl-auto=validate` only — never create/create-drop/update — and reject in-memory runtime modes; verify the migration chain actually applies against real PostgreSQL from empty. Confidence: 0.8
- Money must use decimal/BigDecimal arithmetic with explicit rounding and no floating point, and financial edge cases (zero, partial, exact, overpayment, voided, overdue, large, decimal amounts) must be tested. Confidence: 0.8
- Verify data/UI consistency: for every KPI, trace PostgreSQL query = API response = displayed value; never accept a visual value without tracing it to real data. Confidence: 0.8
- Accessibility and responsiveness are real acceptance gates (with automated a11y testing and breakpoint checks); do not suppress rules or skip checks to make tests pass. Confidence: 0.8
- Products should carry their own distinctive premium visual identity rather than reusing a sibling's; extend an existing tokenized design system rather than scattering hardcoded colors, and avoid excessive animation/rainbow styling. Confidence: 0.75
- Design composition should be varied and deliberate (different surfaces and section layouts) rather than rows of identical cards. Confidence: 0.65
- Drive an initiative all the way to a complete, production-ready product in one continuous effort — completing one layer (e.g. "backend implemented", "frontend renders", "tests compile") is not a stopping point while the rest of the acceptance matrix remains. Confidence: 0.8
- Before declaring a product complete, scan the entire project for contamination from sibling projects — stale branding, old routes/API paths, unrelated database names — and expect zero. Confidence: 0.65
- Ship a standard documentation set for each product (README, ARCHITECTURE, DATABASE, API_SPEC, DEPLOYMENT, TESTING, RUNBOOK) covering prerequisites, env vars, startup, migrations, roles/permissions, APIs, production build and troubleshooting, with no real credentials. Confidence: 0.6
- Organize a frontend around one centralized, typed API client: pages never build URLs or call fetch directly, service modules carry the endpoints, types mirror the real backend DTOs (never invent a field), and screens are split into reusable components rather than one monolithic component. Confidence: 0.8
- Never defang the type system to make a build pass: fixing frontend/backend type drift means correcting the type to the real DTO — not marking fields optional everywhere, not `any`, not casting through `unknown as`. Confidence: 0.8
- Never convey a status or state by colour alone — pair every colour cue with a written label, and use design tokens rather than hex literals or a raw palette. Confidence: 0.75
- Only expose UI for functionality that actually exists: no navigation entries, routes, buttons or toggles pointing at unimplemented features, and no placeholder controls that do nothing. Confidence: 0.8
- The backend is the single source of business/financial truth: render server-computed values (settlement, outstanding, totals, derived metrics) exactly as returned and never recompute or duplicate that logic in the client. Confidence: 0.8
- Verify a frontend end-to-end in a real browser against the real backend (every route loads real data, console and network clean, mutations actually exercised), not merely typecheck/build/unit tests. Confidence: 0.75
- Do not make unrequested repository-state changes such as `git init` without authorization; if no repository exists, document that fact and do not let it block the work. Confidence: 0.8
- Own the deliverable: verify that delegated or parallel work actually produced its artifacts, and take work over directly rather than repeating a delegation that silently produced nothing. Confidence: 0.7
- Every chart must be backed by real data and answer a business question, with labels, units, a legend and a genuine empty state — no decorative charts added just to look impressive. Confidence: 0.6
- Fix a whole class of defect at the shared primitive / root cause so no future screen can reintroduce it, rather than patching each offending page (e.g. a layout containment fix in the reusable Panel component). Confidence: 0.7
- For auth sessions, prefer proactive refresh driven by the backend-supplied `expiresInSeconds` (renewing before expiry with a skew) over reacting to a 401; an expected console/network error that the app silently recovers from is still a defect. Confidence: 0.7
- Code should carry substantial comments explaining WHY (root cause, contract, tradeoff, what would otherwise break), not restatements of what the code does. Confidence: 0.6
- Run verification in an isolated, ephemeral environment (own container, non-default port) so the user's local services and data are never touched or destroyed; verify afterwards that their ports/database are untouched and clean up the temporary environment. Confidence: 0.75
- Verify write/mutation workflows for real rather than inferring them from a rendered button: exercise the action, then confirm at every layer — HTTP status, UI feedback and refreshed state, database row, history/audit record — and use throwaway or safe records that can be restored instead of disturbing seeded data. Confidence: 0.75
- Verify against the production artifacts (built/packageable backend run with production configuration, production frontend build) — never treat dev-server results as the final production result. Confidence: 0.7
- When testing authorization/IDOR, include positive controls: show a permitted role succeeding on the same record so a refusal is demonstrably authorization and not absence, and beware probes that fail earlier in the stack (body validation returning 400 before method security) — they prove nothing about permissions. Confidence: 0.7
- Report verification as explicit matrices (route × load/data/API/console/interaction, role × endpoint) carrying actual HTTP statuses, so every item has evidence and nothing passes merely because it compiled. Confidence: 0.65
- Distinguish deliberate documentation (e.g. design-rationale comments that reference sibling products) from real contamination, and never delete useful rationale or apply broad ignore patterns just to make a scan result look cleaner. Confidence: 0.7
- Centralize user-facing error messages: every known error code maps to a friendly message instead of inline fallback sentences, internal codes are not exposed, the response envelope stays consistent, and a regression test pins this. Confidence: 0.6
- In a final acceptance/ship-gate phase, freeze the architecture: make only targeted changes required by actual findings, and never regenerate migrations, redesign the product, or replace working components. Confidence: 0.7
- Verify parameterized/detail routes by driving them directly with real IDs fetched from the live API rather than inferring coverage from harvested links or hrefs. Confidence: 0.6
- When a requirement's stated count disagrees with its itemized list, call out the discrepancy explicitly and verify every enumerated item rather than trusting the number. Confidence: 0.6
- For scoped list endpoints, confirm authorization/scope filtering is applied before pagination so unauthorized records cannot influence counts or page sizes. Confidence: 0.6
- Any source change invalidates previously-passed verification gates: an accessibility/responsive/regression pass run against an earlier build cannot be claimed for the current one, so those gates must be re-run on the final build before acceptance. Confidence: 0.7

- Bias to action over prolonged analysis: follow an "inspect → fix → test → verify" loop, do not spend an entire session/turn analyzing a straightforward problem, and do not redo already-verified work unnecessarily. Confidence: 0.8
- Prefer the smallest change that fixes a real problem; do not add speculative architecture or unnecessary abstractions, and do not rename backend fields or reshape existing API contracts (or redesign the visual system) merely to accommodate the UI. Confidence: 0.8

Confidence: 0.8
